## Resolved-snapshot B: semantics and limits

NuGet's lock builder iterates resolved package libraries for each target and marks
a package Direct when its identity appears in that framework's PackageSpec
dependencies, retaining the requested range. It does not copy literal csproj
nodes or distinguish explicit from SDK-added dependencies at that point.
RID targets can be deltas from the base framework, and current CPM/alias features
use newer lock versions. A supported snapshot must not merge those graphs or
project closure into one Direct population. [NuGet lock builder](https://raw.githubusercontent.com/NuGet/NuGet.Client/dev/src/NuGet.Core/NuGet.Commands/PackagesLockFileBuilder.cs).

The original lock design separately defines Direct, Transitive and Project,
per-framework graphs and RID deltas. Schema1 Direct is therefore meaningful
producer-recorded package directness for its recorded target, **not necessarily
literal explicit directness** and not the union of all possible project contexts.
[NuGet lock design](https://github.com/NuGet/Home/wiki/Repeatable-build-using-lock-file-implementation).
Current upstream development source is corroboration of artifact semantics,
not proof of the exact OASim historical SDK implementation. The retained Phase2
four-view experiment separately observed no extra implicit top-level entries.

Answers to the eight product questions:

1. Yes, for a valid producer snapshot, Direct describes its direct package
   dependencies in the recorded graph; it does not prove explicit-only scope,
   current project identity or complete evaluated contexts from schema alone.
2. Conditions/imports may change the evaluated package set without recording
   their expressions/values. CPM may change requests or kinds/schema. Multiple
   TFM/RID keys expose some context distinctions; configuration/OS/SDK/property
   values, omitted contexts and implicit classification can remain invisible.
3. Yes, a stale lock may retain a removed direct package or old request/version.
4. Yes, a current added PackageReference may be absent from a stale lock.
5. Minimum: whole supported framing; exact lock identity/bytes; explicit project
   association; named sole recorded framework/no-RID context; accepted evidence
   that Direct is complete for the claimed explicit external snapshot scope;
   checks of statically knowable requests/framework/identities; known conflict
   refusal; separate package namespace authority. Project-byte digests bind an
   assertion to inputs, not the truth of producing/evaluated history.
6. A snapshot claim can avoid complete interpretation of current declarations.
   It still requires **snapshot-population completeness**, truthful context,
   and explicit acceptance of that narrower basis. It cannot simply inherit
   current v2's successful static ProjectContext requirement or claim that an
   old lock covers current changes. Any current-file association must be made
   accountable, not inferred from co-location.
7. The arithmetic is unchanged. NuGet's admission/directness convention changes
   prospectively; that requires human authority and visible basis. Ruby ordinary
   locks already supply directness; npm/Python still use declaration populations.
8. The lock proves no acquisition origin, artifact/public content correspondence,
   current restore/build success, deployment, reproducibility, unused-code status,
   compatibility, current declaration completeness or applicable public namespace.

Microsoft documents updating locks after dependency changes and locked-mode
failure on inconsistency. Libyears does not run that check; no restore success
is inferred. [NU1004 examples](https://learn.microsoft.com/en-us/nuget/reference/errors-and-warnings/nu1004),
[lock behavior](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files#locking-dependencies).
